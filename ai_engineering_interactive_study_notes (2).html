Module 1 • Basics of LLMs

Large Language Models, Frozen Weights & Knowledge Cut-Off

Foundations

What Is a Large Language Model?

A Large Language Model (LLM) is a deep neural network—built on the Transformer architecture—trained on massive text corpora to model statistical language patterns and predict the next token in a sequence.

  • •Massive Scale: Billions of learned numerical parameters (weights) encoding grammar, world facts, and reasoning patterns.
  • •General-Purpose: A single model performs summarization, drafting, translation, coding, and question answering.
  • •Probabilistic Output: Generates fluent text by estimating token probabilities rather than querying a verified database.

What Is a Frozen Model?

Once pre-training and alignment conclude, an LLM's internal parameters are locked—making it a frozen model during deployment and everyday inferencing.

  • •Static Parameters: User prompts and conversations never permanently alter the model's trained weights.
  • •No Automatic Learning: Facts taught in one session disappear when a fresh session begins unless injected as context.
  • •Predictable Behavior: Freezing weights ensures consistent, auditable output and avoids unintended model drift.

Knowledge Cut-Off & Its Limitations

The knowledge cut-off is the latest date of training data absorbed before the model was frozen (e.g., March 2024).

  • •Significance: Establishes the temporal boundary for facts, standards, and scientific knowledge stored inside weights.
  • •Stale Information: Cannot know newly approved drugs, updated clinical guidelines, or recent events.
  • •Hallucination Risk: Pressed on post-cutoff or private facts, a standalone LLM may fabricate plausible-sounding errors.

Open-Weight vs. Proprietary LLMs & Healthcare Applications

Model Types & Domain Impact

Open-Weight LLMs

Downloadable Weights

Models whose trained parameter weights are publicly released. Organizations can download, self-host on private infrastructure, audit, quantize, and fine-tune them for specialized domains.

Examples: Meta Llama 3 Mistral / Mixtral Google Gemma Qwen

Proprietary (Closed) LLMs

Managed Cloud API

Commercial models whose architecture details and trained weights remain private. Users interact with them exclusively through vendor-hosted web apps or pay-as-you-go APIs.

Examples: OpenAI GPT-4o Anthropic Claude Google Gemini

Module 2 • LLM Inferencing

Inferencing, Prompts, Tokenisation & Embeddings

Interactive Tokeniser

Inferencing

The runtime phase where a trained LLM accepts an input prompt and runs forward computations to generate a text response—keeping all weights fixed.

Prompt

The input text (instructions, role framing, context, or constraints) given to the LLM. It steers next-token probabilities to control accuracy, tone, and structure.

Tokenisation

Splitting text into subword units (tokens, e.g., via Byte-Pair Encoding) and mapping each to an integer ID so neural networks can process text numerically and handle rare words.

Embeddings

Dense numerical vectors encoding semantic meaning. Related concepts (e.g., doctor and physician) sit close together in high-dimensional vector space.

Module 3 • Local & Cloud Inferencing

Local vs. Cloud-Based LLM Inferencing

Deployment Architecture

Local Inferencing

Running an open-weight model directly on your own laptop, workstation, or on-premise server (e.g., via Ollama or llama.cpp). Prompts and outputs stay completely inside your local network.

Cloud-Based Inferencing

Sending prompts over HTTPS to remote GPU clusters hosted by AI providers or gateways (e.g., OpenRouter, OpenAI, Anthropic, Google). Provides instant access to frontier-scale models with zero local GPU setup.

Core Trade-Offs: Local vs. Cloud

Dimension Local Inferencing Cloud Inferencing
Privacy Maximum control; sensitive data stays strictly on-device or behind local firewalls. Data travels to external servers; requires vendor trust, encryption, and compliance agreements (e.g., BAA).
Cost Upfront hardware & electricity cost; $0 per token at runtime. No upfront GPU purchase; pay-per-token API billing scales with usage volume.
Hardware Requires sufficient RAM / GPU VRAM (8–64+ GB depending on model size & quantization). Minimal client hardware—runs from any lightweight laptop, browser, or mobile app.
Accessibility Works completely offline; requires local setup and model downloads. Requires active internet connection; instant access to largest frontier models.

Module 4 • Retrieval-Augmented Generation (RAG)

            
Text Similarity, Embeddings & Vector Databases

          

          Interactive Vector Lab
        


        

          

            
Text Similarity

            

              Measures semantic closeness beyond exact keywords. Typically computed via Cosine Similarity (angle between vectors: 1.0 = identical meaning, 0.0 = unrelated).
            

          

          

            
Role of Embeddings in RAG

            

              Both document chunks and user queries pass through the same embedding model into shared vector space, so "heart attack" matches "myocardial infarction".
            

          

          

            
Vector Databases

            

              Specialized stores (Chroma, FAISS, Pinecone, pgvector) saving [Vector + Raw Chunk + Metadata] and retrieving Top-K nearest neighbors in milliseconds.

Module 5 • Tool Calling & MCP

            
Tool Calling: Bridging Language Models & Live Actions

          

          

            
            
          

        


        

          

            

              
Why Tool Calling Is Required

              

                Even with RAG, an LLM only reads indexed text—it cannot natively query live APIs, execute deterministic math, check real-time schedules, or trigger external actions.
              

              
    
                
  • • Real-Time Data: Fetches live lab values, inventory, or database records.
    • 
                
  • • Deterministic Accuracy: Delegates formulas (e.g., eGFR, dosage) to verified code.
    • 
                
  • • Action Execution: Books appointments, triggers alerts, or updates records safely.
    • 
              

            


            

              
Critical Execution Boundary

              

                The LLM never executes code or APIs directly. It only emits a structured JSON request naming the tool and arguments. The host application validates permissions, runs the function, and passes the result back to the LLM.

Module 5 • Model Context Protocol (MCP)

            
Model Context Protocol (MCP): Architecture & Core Primitives

          

          USB-C for AI Applications
        


        

          The Model Context Protocol (MCP) is an open, JSON-RPC 2.0 standard that defines a universal way for AI applications to discover and interact with external tools, databases, and context sources—eliminating brittle custom glue code between every model and every API.

What an MCP Server Exposes: 3 Standardized Primitives

          

            

              

                1. Tools
                Model-Controlled
              

              
Executable functions the LLM can call with structured arguments to query live APIs, run calculations, or trigger actions (e.g., get_latest_lab).

            

            

              

                2. Resources
                App-Controlled
              

              
Read-only contextual data addressed via URIs—such as documents, database schemas, or patient summaries (e.g., ehr://patient/1042).

            

            

              

                3. Prompts
                User-Controlled
              

              
Reusable, server-defined prompt templates that guide consistent multi-step workflows (e.g., /discharge-summary or /drug-review).
